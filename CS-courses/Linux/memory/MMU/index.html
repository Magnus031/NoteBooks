    MMU

    由于是因为在复习操作系统，现在来介绍一下 Linux 中的 MMU (Memory Management Unit)（内存管理单元）相关内容。

    Introduce

    问题如下:

    问 virtual memory space 到 physical memory space 的转换。回答了每个进程有个页表，寻址时通过 MMU 转换。问 MMU 是纯软件还是硬件的。问页表存储在哪。如何加速地址转换的过程。问如果虚拟地址对应的物理地址不在内存里会怎么样。问内核处理完 page fault 之后会怎么样。

mappages(pagetable_t pagetable, uint64 va, uint64 size, uint64 pa, int perm)
{
  uint64 a, last;
  pte_t *pte;

  if(size == 0)
    panic("mappages: size");

  a = PGROUNDDOWN(va);
  last = PGROUNDDOWN(va + size - 1);
  for(;;){
    if((pte = walk(pagetable, a, 1)) == 0)
      return -1;
    if(*pte & PTE_V)
      panic("mappages: remap");
    *pte = PA2PTE(pa) | perm | PTE_V;
    if(a == last)
      break;
    a += PGSIZE;
    pa += PGSIZE;
  }
  return 0;
}

    是用来建立页表映射关系的，它是一个软件层面的实现。MMU 在硬件层面上使用这些映射关系来进行地址转换。

    页表存放的位置

    在 RISC-V 架构中，页表是存放在 satp 寄存器中的, 而在 x86 架构中，页表存放在 CR3 寄存器中，MMU 也会通过读取这些寄存器来获取页表信息。

    如何加速地址转换的过程

    主要的思路就是，首先我们看一下当前是如何查表的？

    • 多级页表，如果我们要查找一个虚拟地址对应的物理地址，需要经过多级页表的查找过程，这个过程是比较耗时的。

    方法1 选择利用TLB加快页表查询

    所以我们选择了 TLB （Translation Lookaside Buffer）来加速地址转换的过程。 选择 TLB 是可以及时记录频繁被查找的虚拟地址的映射，那么就可以把次数减少到1次, 这个过程是自动的:

    1. 当 CPU 生成了一个虚拟地址的时候，MMU 会首先检查 TLB 中是否有这个虚拟地址的映射关系。
    2. 如果 TLB 中有这个映射关系，那么 MMU 就可以直接使用这个映射关系来转换虚拟地址到物理地址，这个过程是非常快速的。
    3. 如果不存在(TLB miss)，那么就会执行常规的多级页表遍历。找到映射之后，MMU会将这个新的映射关系存入 TLB 中，以便下次使用。

    Trade-off: 虽然这个过程是自动的，但是是需要操作系统定时维护 TLB 的，比如在完成上下文切换的时候，需要刷新TLB，不然的话访问的可能是别的进程的页表中的虚拟地址映射关系了

    方法2 选择使用大页来加速地址转换

    常规的内存页大小是 4KB，大页则表示的是更大的内存页，比如 2MB, 1GB这样

    本质就是通过减少页表项的个数，需要保存在TLB中的映射条目数量大大减少

    内存找不到咋办（？发生缺页错误

    1. 虚拟地址对应的物理地址不在内存中

    当CPU生成一个虚拟地址，MMU根据页表进行翻译时，它发现页表项（Page Table Entry）中的有效位（valid bit）被设置为无效。

    这个“无效”标志告诉MMU： * 这个虚拟地址是合法的，它确实属于该进程的地址空间。 * 但它所对应的物理页帧目前不在主内存（RAM）中。

    这种情况通常发生在操作系统为了腾出内存空间，将不经常使用的物理页帧的内容换出（swap out）到磁盘（如硬盘或固态硬盘）上的一个交换文件（swap file）或交换分区（swap partition）中。

    2. 触发缺页错误（Page Fault）

    当MMU遇到一个无效的页表项时，它无法完成地址翻译。它会立即通知CPU，触发一个缺页错误（Page Fault）中断。这个中断会将CPU的控制权从当前进程转移到操作系统内核的中断处理程序（Interrupt Handler）。

    3. 内核处理Page Fault

    内核的缺页错误处理程序会执行以下一系列操作：

    1. 保存现场：首先，内核会保存当前进程的CPU状态（寄存器等），以便之后能恢复执行。
    2. 查找缺页：内核会根据MMU提供的虚拟地址和错误类型，确定是哪个虚拟页发生了缺页。
    3. 定位物理页：内核会通过自己的数据结构（比如页帧管理表），找到该虚拟页之前被换出到磁盘上的位置。
    4. 分配内存：内核会在主内存中找到一个空闲的物理页帧。如果找不到，它会启动页面置换（Page Replacement）算法，从内存中选择一个不常用的物理页，将其内容换出到磁盘，从而腾出空间。
    5. 从磁盘读入：内核会发起I/O操作，将磁盘上相应页的内容加载到新分配的物理页帧中。
    6. 更新页表：一旦数据从磁盘加载到物理内存，内核会更新该进程的页表。它将之前无效的页表项的有效位设置为有效，并将新物理页帧的地址填入其中。

    4. 跳回并重新执行

    内核完成上述所有步骤后，它不会像其他中断处理程序那样直接返回，而是会跳回到导致缺页错误的那条指令。

    CPU会重新执行这条指令。这一次，当MMU再次进行地址翻译时，它会发现页表已经被更新，新的映射是有效的。地址翻译会成功完成，指令得以正常执行，进程也可以继续运行，对它来说，仿佛什么都没有发生过一样。

    这个过程对应用程序是完全透明的，应用程序并不知道它的数据曾经被换出到了磁盘。这就是虚拟内存（Virtual Memory）为应用程序提供的强大抽象能力。

    缺页错误

    其实是分成了 软缺页 和 硬缺页 两种情况

    软缺页

    软缺页是指当一个进程访问一个虚拟地址时，它发现该虚拟页确实没有在当前的页表中建立映射,但它的 所对应的物理页仍然位于主内存中.

    你提出的问题非常关键，它直接触及了虚拟内存管理中最容易混淆的两个概念。你的直觉是正确的，但让我们更精确地来理解“物理内存中缺页”和“没有建立映射”这两个状态。

    你问得非常好：“为什么物理页帧在内存里，却没有建立映射？” 这正是软缺页的精妙之处。

    软缺页的产生并非因为内存不足，而是因为操作系统为了效率和资源共享，采取了延迟映射（Lazy Mapping）的策略。

    我们用两个具体的例子来解释：

    1. 共享库的延迟加载

      • 情况：假设 Process A 和 Process B 都需要使用 C 标准库（libc.so）。
      • 优化：为了节省内存，操作系统只会将 libc.so 的代码加载到物理内存中一份。
      • 软缺页的产生：Process A 和 Process B 的页表一开始都没有指向这块物理内存的映射。当 Process A 第一次调用 libc.so 中的某个函数时，它访问的虚拟地址没有对应的页表项。
      • 内核处理：此时发生软缺页。内核发现 libc.so 的物理页帧已经在内存中。它不需要访问磁盘，而是直接在 Process A 的页表中创建一个新的页表项，将其虚拟地址映射到 libc.so 的物理页帧上。
      • 结果：后续 Process A 访问 libc.so 都将是TLB命中或正常的地址转换，而 Process B 也会以同样的方式建立自己的映射。

    2. 写时复制（Copy-on-Write, COW）

      • 情况：在 fork() 操作中，父子进程一开始共享相同的物理内存页，但页表项被设置为只读。
      • 软缺页的产生：当子进程或父进程试图写入这些共享的物理页时，MMU会因为权限违规而触发一个软缺页。
      • 内核处理：内核的缺页处理程序识别出这是一个COW错误。它不会从磁盘加载，而是：
        1. 在内存中分配一个新的物理页帧。
        2. 将旧页的内容复制到这个新页帧中。
        3. 更新当前进程的页表，将该虚拟地址映射到新的物理页帧上，并将权限设置为可读写。
      • 结果：父子进程现在有了各自独立的内存页，可以进行修改，而没有在 fork() 时产生额外的开销。

    所以，简单来说：

    • 硬缺页：是由于内存不足导致的，数据在磁盘上。
    • 软缺页：是由于操作系统策略（如共享、延迟分配）导致的，数据在内存中，只是页表没有指向它。

    硬缺页

    主要缺页 硬缺页是指当一个进程访问一个虚拟页时，在物理内存上找不到，并且它的内容以及被换出到了磁盘上

    你提出的问题非常关键，它直接触及了虚拟内存管理中最容易混淆的两个概念。你的直觉是正确的，但让我们更精确地来理解“物理内存中缺页”和“没有建立映射”这两个状态。

    硬缺页：物理页帧已被换出到磁盘

    “物理内存中缺页” 这个状态指的是：

    1. 这个虚拟页曾经在主内存中，并且有对应的页表映射。
    2. 但由于主内存空间不足，操作系统需要为新的进程或数据腾出空间。
    3. 根据页面置换算法（如LRU，最近最少使用），操作系统选择一个“不常用”的物理页帧，将其内容写入磁盘的交换空间（swap space）进行备份。
    4. 然后，操作系统会清空该物理页帧，并将其对应的页表项标记为无效（invalid）或将它指向磁盘上的位置。

    当进程再次访问这个虚拟地址时，MMU发现该页表项无效，从而触发硬缺页。内核就知道它需要从磁盘上把数据重新加载回来。这个过程因为涉及缓慢的磁盘I/O，所以开销非常大。

    如何处理硬缺页呢？

    其实主要就是 swap 将磁盘中的数据 swap 到物理内存中

    1. 从磁盘上定位该页的数据
    2. 发起一个 IO 请求，将数据从磁盘加载到物理内存中
    3. 等待 IO 请求的完成
    4. 更新页表，将新的物理地址与有效位写入

    处理完缺页错误 接下来会发生什么

    1. 更新页表， 也就是将新的物理页帧地址写入页表，并设置有效位，以及更新权限。
    2. 刷新 TLB, 因为这个虚拟地址的映射关系已经改变，所以需要将 TLB 中的旧映射关系清除，以便下次访问时能使用新的映射。
    3. 恢复CPU的状态， 因为在发生中断之前，会记录下当前的 CPU 状态（寄存器等），所以需要将这些状态恢复。
    4. 重新执行中断指令
