    日志

    现在讲一下 Mysql 中的日志

    Introduce

    日志 在数据库中是具有十分重要的作用，尤其是在恢复数据，问题排查，性能优化的时候都需要通过 从日志中来获取信息作为依据。在Mysql中很多事情都需要利用日志来实现:

    • 回滚事务 -> undoLog
    • 提交事务 -> redoLog
    • MVCC机制
    • 数据迁移与备份

    UndoLog 回滚日志

    目的 : 保证了事务的原子性，也就是说事务的回滚操作是可以保证的。是引擎层生成的日志，记录的是逻辑操作，也就是增删改的逆操作。

    作用 :

    1. 事务回滚
    2. MVCC 的 readView 需要使用到 undoLog 来获取事务开始时候的数据

    具体细节

    1. Insert 操作，会在 undoLog 中插入主键 id,等回滚的时候，就只需要直接的用 delete 本条记录的操作就可以了。

    2. Update 操作，会记录一条相反的 Update 的回滚日志，我们在回滚的时候，只需要执行这个 Update 操作就可以了。

    3. Delete 操作，我们只需要记录删除前的内容，然后回滚的时候 Insert 原来的数据就行了。

    隐式事务

    其实就是 autocommit，我们把事务的开启与提交都交给了 Mysql 来处理

    显式事务

    其实就是我们手动来规定事务的开始与结束，使用 BEGIN,COMMIT,ROLLBACK 来进行事务的操作。

    1
2
3
    BEGIN
sql statement;
COMMIT;

    事务回滚

    一条记录中记录的 undoLog 都会记录 roll_pointer 指向的是上一个版本的记录，和一个 trx_id 用来记录当前的事务ID。

    从事实上说，其实Mysql在回滚的时候并不会执行 反向sql 操作，而是直接将 roll_pointer 回滚到指向的 undo 记录

    比如你执行的是 Update salary = 1000 -> 1200，那么 undo 就会记录的是 1000 是旧值，方便我们进行回滚。

    Redo Log

    目的 : 保证了事务的持久性，也就是一旦提交了，那么就会永久的保存下来了。主要保存的是 新值(修改后的数据或变更操作),以便系统在崩溃后重启的时候，可以通过 redoLog 来恢复数据。

    比如你执行的是 Update salary = 1000 -> 1200，那么 redo 就会记录的是 1200 是新值。以便将来对数据页进行 redo 操作。我们在恢复数据的时候，只需要将数据库的数据恢复到我们最近的版本即可。

    主要用途

    1. 崩溃恢复 这个很好理解，我们只需要重新的执行 redo 操作，就可以恢复数据

    2. 保证写性能 大多数的数据库会先将修改的操作写入 顺序的 I/O redo 日志中，再异步的把实际数据页写到磁盘中(Write-Ahead Logging)

      (WAL机制的作用)即使系统崩溃，脏盘刷盘失败，我们依旧可以通过redo log来恢复数据到最新的版本。

    每次我们在事务提交前，都必须有一步操作是 强制将Redo日志同步到落盘中，保证未来崩溃后可以按照日志进行重做

    CheckPoint

    redo log 通常会存储在 data 目录下的两个文件中:

    • ib_logfile0
    • ib_logfile1

    当然也可以通过 innodb_log_file_size 和 innodb_log_files_in_group 来设置文件个数。

    我们看上图，其实就可以知道，redoLog 其实是分成两个文件进行环形存储的。最主要的功能实现是通过两个指针:

    • write_pos : 表示的是当前更新到的位置，也就是此时 redo log文件写到了哪个位置
    • check point : 指的是哪些 redolog 记录已经失效了，也就是已经被刷到磁盘中了。

    那么看上图，其实就很好理解了，在 write-pos 和 checkpoint 之间的区域(顺时针),其实就是可以用来继续新的操作了。也就是可以进行新的 redo 日志的写入了。

    而 checkpoint 到 write-pos 之间的区域就是虽然写入了 redolog 的buffer，但是还没有刷到磁盘中的数据。

    如果 write_pos 赶上了 checkpoint 怎么办？

    很好解决，那么就是阻塞mysql,可以让新的事务等待，直到有足够的空间可以进行新的 redo 日志的写入。因为此时我们已经没有区域可以写入新的 redolog 了，为了保证持久性，我们选择等待，牺牲性能来换取数据的安全性。

    等buffer pool 中存在哪些脏数据已经成功的写入磁盘了，我们再通更改 checkpoint 的位置，来进行后续的事务。也就是可以继续的插入redo_log 了。

    刷盘的时机

    目的 : 其实刷盘很好理解，就是定期的将在 buffer 中的数据写入磁盘中，从而保证了数据的持久化。通常会有几种情况:

    1. redoLog buffer : 当 redoLog buffer 写满了，那么就需要将其刷盘了。不然无法继续写入新的 redoLog 了。

    2. 事务提交的时候，为了保存持久性，必须要把页面修改时候的 redoLog 刷到磁盘中。否则系统崩溃的时候后，无法将该事务对页面所做的修改恢复过来。

    3. 将某个脏页的数据刷新到磁盘之前，redo日志会刷新到磁盘中

    4. 后台线程 大概会以每秒一次的频率将脏页刷到磁盘中。

    5. 触发checkpoint
